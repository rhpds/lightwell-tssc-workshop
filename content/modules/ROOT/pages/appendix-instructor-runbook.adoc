= Appendix: instructor delivery guide
:toc:
:toclevels: 2

Use this guide to prepare and facilitate the workshop. Students follow the seven tracks in navigation; this appendix explains the suggested two-day grouping, the evidence to review at each handoff, and how to handle incomplete work.

== Plan the two-day sequence

Start with Tracks 1–3 on Day 1 and Tracks 4–7 on Day 2. This grouping separates input selection and source ownership from build, signing, promotion, and compliance. It is a planning starting point, not a measured duration. Record actual timings during dry runs and move whole track boundaries if necessary.

image::appendix-delivery-days.svg[Day 1 produces verified inputs and reviewed source; Day 2 builds signs promotes and assesses the same application,width=700,link=self,window=blank]

There are six learner module pages in Tracks 1–3 and eleven in Tracks 4–7, plus the workshop introduction. The count does not imply equal effort per module. Retain the sequence and its evidence handoffs when adjusting the schedule.

== Prepare the environment

Before learners begin, confirm that Showroom can reach the claim and that the bastion connection needed for Track 1 is available. Inspect the provisioned service URLs and access information without placing credentials in shared notes.

Check that the Maven starter repository, Developer Hub template and `publish:gitea` action, Renovate integration, pipeline Tasks, and security services are ready. Use the repository's existing instructor health-check procedures. Repair missing provisioning before asking learners to repeat an exercise; preserve their repositories and evidence on retries.

== Guide troubleshooting with direct evidence

Classic Showroom allows learners to open later pages. Explain that the exercise dependencies still apply even though navigation is unrestricted.

Tracks 1–4, 6, and 7 review command output, repository history, and saved evidence directly. Track 5 retains module-specific report fields and validation Jobs in `lw-poc-validate`; its pages explain retries. There is no automated Solve procedure or attempt quota.

For a failed step, identify the exact resource, namespace, run, and image before troubleshooting. Separate configuration mistakes from authentication, connectivity, and service readiness problems. A timeout or `ImagePullBackOff` alone does not prove that the intended security control rejected an artifact.

In Track 7, `LW-DEMO-0002` is a seeded sample. A failed ACS command may be a policy rejection or an execution error; inspect the logs before accepting the assessment as complete.

== Preserve deliberate sample versions

The affected and remediated fixtures support the comparison in Track 2. Review dependency-update proposals against the teaching purpose before changing those versions. A routine upgrade of the affected fixture can remove the intended demonstration. The learner's Renovate PR in Track 3 is a separate, deliberate part of the exercise.

== After the event

Record timings, prerequisite failures, and recurring points of confusion. Use that evidence to adjust future delivery. Optional references can be read afterward; do not remove a required handoff simply to fit the schedule.

Use xref:appendix-enablement-checklist.adoc[Delivery readiness review] for the follow-up discussion. Ask learners to show evidence and explain its limits, then map the workshop to customer requirements with xref:appendix-consultant-delivery.adoc[Consultant delivery map].

== Verify session continuity before delivery

On a disposable test claim, follow module 3.2 until the application clone exists, leave an uncommitted marker file in it, and save the Track 5 key and Track 6 verification evidence in their documented home directories. Record file checksums and `git status --short` without recording credentials or the private key contents. Replace only the Showroom pod, leaving its home PVC intact. In the new terminal, confirm the marker, Git status, key checksums, and evidence checksums are unchanged. Resume the next module after rediscovering its variables and refreshing Git and registry authentication. Record this result as part of delivery readiness; a successful remote clone alone does not test preservation of uncommitted work.
