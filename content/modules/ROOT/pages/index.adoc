= Lightwell Software Supply Chain Security Workshop
:toc:
:toclevels: 2

You are about to walk *one* trusted software supply chain on a dedicated OpenShift cluster and prove, for a single production container, where the base came from, which libraries you compiled in, which git source repository recorded the runtime base, and the libraries compiled into the application, how the build stayed inside the trust boundary, who signed the image, which digest production is allowed to run, and how a known CVE shows up as remediated. 

The workshop has seven tracks. You verify a Hummingbird base, consume Lightwell dependencies, own the application source, build hermetically, sign and attest, promote a production container, then prove continuous compliance.

image::seven-track-tssc-flow.png[Seven-track TSSC flow — Hummingbird through continuous compliance,width=700,link=self,window=blank]

You build an example application that serves a greeting over HTTP: a request to `/api/greeting` returns a hello message for the name you send. The application is written in Java and built with Maven, and that Maven build is the one you complete. Maven compiles the application and downloads its libraries. `settings.xml` points Maven at the enterprise proxy on this cluster, an in-cluster Nexus. You then use the library at an exact `.rhlw-*` version, which is Lightwell's security backport on the upstream line you already run. That version is the coordinate later modules sign, admit, and explain in the vulnerability report.

We use Java, Maven, an artifact manager such as Artifactory, and in-cluster Gitea. On this cluster the artifact manager is Nexus. Customers often run Artifactory for that same proxy. We call out Python and JavaScript. You read the callout and continue with Java, Maven, Nexus, and Gitea.

* Python uses `pip.conf` the way this workshop uses `settings.xml`. The remediated version suffix looks like `1.0.0+rhlw.00001` on a `requirements.txt` line.
* JavaScript libraries follow the same pattern: an enterprise npm registry, and an exact package version. You can describe that pattern to a customer. This cluster has no npm exercise.

Hands-on work starts at xref:module-01-hummingbird-verify.adoc[1.1 Verify Hummingbird]. There you discover the published Hummingbird pull spec and run `cosign verify` against it.

== What a trusted software supply chain proves

A *trusted software supply chain* (TSSC) is the set of controls that let you answer three questions for every production container. What went into the image? Who built it and signed it? Are known vulnerabilities remediated, without treating the public internet as a trusted input?

On OpenShift, Red Hat TSSC is those controls as products you will actually open in this workshop:

* Signed and attested artifacts, in link:{docs-rhtas-url}[Red Hat Trusted Artifact Signer^]
* A system of record for SBOMs and advisories, in link:{docs-rhtpa-url}[Red Hat Trusted Profile Analyzer^]
* Runtime and pipeline policy, in link:{docs-rhacs-url}[Red Hat Advanced Cluster Security^] and in Conforma, the Enterprise Contract CLI `ec`
* Promotion by Git, in link:{docs-gitops-url}[OpenShift GitOps^]
* A golden path for the application repo, in link:{docs-rhdh-url}[Red Hat Developer Hub^]

The same stack is what link:{docs-rhtap-tech-url}[Red Hat Trusted Application Pipeline^] describes. You will not install that pipeline as a product. You will use the pieces above, on this cluster, under the names the modules use.

TSSC does not start when a pipeline runs. It starts with *inputs you can name*: a signed runtime base, application libraries from a trusted repository, and source that records both exact versions. An exact version is the full name written in source. For the base, that name is the Hummingbird pull spec, digest included. For a library, that name is a version such as `3.14.0.rhlw-00001`. Hummingbird is the base. Lightwell is the library layer.

== Lightwell Network and Lightwell Clearinghouse Premier

link:{lightwell-product-url}[Lightwell^] is the Red Hat and IBM initiative that maintains *third-party application dependencies*: libraries, frameworks, build tools, and the transitive dependencies those pull in. A scanner can name a CVE that your team cannot upgrade away from, because of certification, compatibility, or a release window. Lightwell supplies a security-only fix on the version you already run.

Lightwell is an annual subscription with two models. This workshop scores the Network path. Clearinghouse Premier is limited availability. You still need both names in a customer conversation, because a Premier remediation lands in the same proxy, the same application source that records that version, and the same evidence store you configure here.

[cols="1,2,2",options="header"]
|===
|Model |What it is |How it shows up in *this* TSSC lab

|*Lightwell Network* (available)
|Consolidated access to Lightwell remediations for eligible open source vulnerabilities. Repositories are *Validated* (upstream-parity, signed, SBOM) and *Remediated* (security-only backports with a `.rhlw-*` version suffix). You consume them through the build and the artifact manager you already have.
|Tracks 2, 3, and 7. You point Maven at an enterprise Nexus proxy, use an exact `.rhlw-*` version named by an OSV `fixed` event, and later file that GAV-bound VEX and SBOM in Trusted Profile Analyzer. Docs: link:{docs-lwn-choose-repo-url}[Choose the right repository^], link:{docs-lwn-java-url}[Configure your Java build tool^]. Console: {lightwell-console-url}.

|*Lightwell Clearinghouse Premier* (limited availability)
|Everything in Network, plus vulnerability reporting and remediation for *member-specific* package versions, verification of novel vulnerabilities, *disclosure handling* for secured patch embargoes, anonymized access to other member requests, and TAM services. It is aimed at pre-selected critical infrastructure, with a broader release planned.
|The same cluster. A Premier remediation is still an exact Maven GAV, or a Python wheel whose version contains `+rhlw`. It has to land in the same enterprise proxy, the same application source that records that version, the same hermetic build, and the same Trusted Profile Analyzer and ACS evidence. Tracks 2, 3, and 7 are the controls you would configure for that member version, including during an embargo: a private proxy, the exact version taken from that GAV, and a delay before public OSV and VEX exist.
|===

== What this workshop does not include

You walk one supply chain on this OpenShift environment. We use Java, Maven, an artifact manager such as Artifactory, and in-cluster Gitea. On this cluster the artifact manager is Nexus, and the application is a Java greeting service. The table is here so you do not lose time looking in the console for a product this cluster deliberately left out. When a customer asks about that product, the right-hand column is the sentence you use, and the module where this workshop already practiced the underlying control.

[cols="1,2",options="header"]
|===
|Not in this workshop
|What you do instead

|Hosted Konflux
|Builds run as *OpenShift Pipelines* (the Task and BuildConfig names on the cluster). Names you may hear in a customer conversation are in xref:appendix-konflux-mapping.adoc[Konflux mapping]. Do not install Konflux.

|A physical air-gap or data diode
|This environment stays on the network. xref:module-14-disconnected-verify.adoc[5.3] is the key-based sign and verify *procedure*. xref:appendix-disconnected-playbook.adoc[Disconnected transfer] is a simulated file drop, not USB or a diode.

|Building Project Hummingbird images
|You *verify and consume* published Red Hat Hardened Images. You do not rebuild the Fedora factory that produces them.

|FIPS certification in the lab
|FIPS is a *product claim* on the image you consume. This workshop does not rebuild an image to produce FIPS evidence.

|JFrog Artifactory, or a Python (FastAPI) application
|We use Java, Maven, Nexus, and in-cluster Gitea. Artifactory is the artifact manager customers often run; you do not install it on this cluster. We call out Python. You do not scaffold a second app.

|A live Clearinghouse Premier membership, member-specific GAV, or embargo window
|You practice the *post-disclosure* Network version and the TSSC controls Premier would reuse (private proxy, exact version, system of record). You do not request a member-only package or sit inside a real embargo on this cluster. Concept: xref:appendix-lightwell-concepts.adoc[Lightwell concepts].

|A customer proof-of-value or certification exam
|This is a *guided workshop*. You practice the flow here. xref:appendix-enablement-checklist.adoc[Internal enablement] is scored *after* the event. It is not a live PoV on this environment.

|A production virtual machine
|You promote a *signed container digest* through GitOps (xref:module-15-gitops-admission.adoc[6.1], xref:module-16-prod-gitops.adoc[6.2]). The same digest can later run on bootc or Satellite; there is no VM to boot here.
|===

== Module Validation

Each module has an in-cluster *Validate Job* in the namespace `lw-poc-validate`. The Job grades the live object you changed and a report ConfigMap token that shows this module was completed. Do the *Your change*. Fill the token. Run the Job. If the Job already exists, delete it, create it again from ConfigMap `validate-job-templates`, and read the logs. There is no Solve, feel free to retry until you succeed.

== Before you start

You read this guide in the RHDP Showroom, which is the lab nav plus an embedded terminal. `oc`, `cosign`, `oc-mirror`, and `ec` are already on `PATH`. Leave GitHub out of the lab: do not curl it for CLIs, and do not use it as the lab git remote. Gitea is in-cluster.

Discover URLs, digests, and passwords from the `lab-*` ConfigMaps. The Checks that grade you are the Validate Jobs in `lw-poc-validate`, and the example above is the one you copy. Never commit credentials: `LW_USERNAME`, `LW_PASSWORD`, `student_password`, or `cosign.key`.
