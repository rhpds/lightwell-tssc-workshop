= 6.1 Deploy the signed image with stage GitOps
:source-highlighter: rouge
:toc:
:toclevels: 2

In this module you prove that stage runs the signed digest, and that an unsigned tag on the same ImageStream fails at pull.

This is the first of the two modules in Track 6, which runs the signed Java application image as the production container and refuses an unsigned digest. You tag the signed image into `lw-poc-staging`, copy the signature onto that repository, commit the digest to the stage GitOps remote, and fill `admission/trust-policy.yaml`. A CronJob renders a namespaced `ImagePolicy` on `lw-poc-staging` and on `lw-poc-prod`. xref:module-16-prod-gitops.adoc[6.2 Promote to prod] is a second Gitea remote. You will update the production GitOps repository in the next module. Keep the staging `app-operate` NetworkPolicy unchanged so the application retains its runtime network access. This policy is separate from the build-pod egress policy you configured in xref:module-10-build-networkpolicy.adoc[4.3 Restrict build-pod network access].

== Why this control exists

Track 5 established which application image you signed and verified. Deployment needs to preserve that choice. Red Hat OpenShift GitOps uses a Git repository to record the desired application state, and Argo CD reconciles that state with the cluster. You commit the verified image digest to `values.yaml` in `lw-student/gitops-spring-boot-lw-poc`; Application `lw-poc-staging` uses that commit to configure the Deployment in namespace `lw-poc-staging`. A digest identifies fixed image content, while a tag such as `latest` can move to a different image. Recording the digest in Git gives you a deployment decision you can review and trace to a commit.

Runtime signature enforcement adds a separate check when a node pulls the image. A Git commit records what you intend to run, but it does not itself verify the image's signature. In this lab, you complete `admission/trust-policy.yaml` in the stage repository, and the cluster renders an `ImagePolicy` for staging and production. The node uses that policy and the public key you published in module 5.3 to check signatures for the protected image repositories. This connects your earlier signing work to the runtime: the application must carry a signature that the configured policy trusts before the node can run it. Signature verification establishes trust in the signed image; it does not inspect its Maven dependencies or establish that the application is free of vulnerabilities.

You demonstrate the control with two outcomes. First, you keep the stage Deployment at zero replicas until the nodes have applied the policy, then start the signed image and confirm that its pod becomes Ready. Next, you create a temporary Deployment using an unsigned digest in the same protected repository. With this lab's native ImagePolicy, creating the Deployment can succeed because enforcement happens when the node pulls the image. The pod then fails to start, and its events must identify a signature rejection. `ImagePullBackOff` alone is insufficient evidence because registry authentication and network failures can produce the same status. Together, the Ready signed pod and the rejected unsigned pull show that staging can run the selected image while enforcing the signature requirement. You carry that verified digest into the separate production GitOps repository in module 6.2.


.GitOps records the deployment choice; node policy enforces the signature requirement.

== How GitOps and runtime policy work together

TrustPolicy is a *workshop-specific input format*, not a portable product API. The admission file you edit on the stage remote is `admission/trust-policy.yaml`, `kind: TrustPolicy`. You set `enforce: true`, the live digest, and the pipeline service-account subject from 5.1. CronJob `trust-policy-apply` in namespace `tssc-admission` polls about every two minutes and renders `ImagePolicy` into both stage and prod. A `ClusterImagePolicy` does not satisfy this workshop’s required ImagePolicy evidence.

Native `ImagePolicy` `signedEmail` has to be an email. The 5.1 identity is a Kubernetes service-account URI, so the CronJob renders `policyType: PublicKey` from ConfigMap `lab-cosign-pubkey`, the `cosign.pub` you published on 5.3. The TrustPolicy file records the 5.1 service-account URI and issuer, but this PublicKey path does not require a matching Fulcio signature. Track 5 verifies that identity separately. `oc tag` copies the image and leaves the `.sig` tags behind. You `cosign copy` those tags, then `cosign sign --key` the destination repository, after the tag.

For the workshop's service-account URI and native PublicKey path, read each field according to its actual control:

[cols="1,1,3",options="header"]
|===
|Input |Treatment |Effect
|`spec.enforce`
|Readiness check
|Must be `true` before the renderer creates the gate. No unresolved placeholders, valid digest syntax, nonempty identity, and scopes are also required. An incomplete input removes the live gate; protect policy edits accordingly.
|`spec.scopes`
|Enforced scope
|Protects the named repositories. The renderer also adds digest-qualified scopes, but retains the repository-wide entries.
|`spec.digest`
|Recorded and syntax-checked
|Must match `sha256:` plus 64 lowercase hex digits. It adds scoped entries but is *not* a one-digest allowlist. GitOps `image.digest` selects the deployment separately.
|`spec.identity.subject` / `issuer`
|Recorded and readiness-checked
|Both must be nonempty. The service-account URI selects PublicKey rendering; these values are not enforced as Fulcio identity constraints on that path. An email subject selects a different renderer branch, outside this exercise.
|`spec.signedIdentity`
|Not read from this input
|The renderer supplies `ExactRepository` from its configured build repository, rather than from the seed block. The resulting signed repository identity is enforced.
|`lab-cosign-pubkey` / `cosign.pub`
|Enforced trust material
|The renderer reads the admission ConfigMap and embeds its public key in the live ImagePolicy. The node requires a matching trusted-key signature and signed repository identity.
|===

A different digest in a protected repository can satisfy the same policy if its signature meets the key and repository requirements. That result does not prove the recorded Fulcio subject signed it or that promotion reviewers approved it. Keep the Track 5 identity-verification output and the GitOps promotion decision as separate evidence.

For a customer handoff, assign signing-key custody and rotation to the signing-service owner, runtime policy and trusted-key updates to platform/security owners, and digest promotion approvals to release owners. Separate their permissions and retain audit evidence. You hold all these roles in this exercise.

The application image already contains the Lightwell dependency versions selected during the build. The runtime policy checks the image signature; it does not evaluate Maven dependency coordinates or whether a dependency comes from Lightwell Network or Lightwell Clearinghouse. An image containing those dependencies must still carry a trusted signature to pass the runtime check.

image::track6-promotion-remotes.svg[Separate stage and production GitOps repositories carry the same verified digest to their own Argo CD Applications,width=700,link=self,window=blank]

As the figure shows, in this module you work the stage remote: `lw-student/gitops-spring-boot-lw-poc`, Application `lw-poc-staging`, namespace `lw-poc-staging`. Module 6.2 works the prod remote. Keep Application `lw-poc-prod` connected to the production repository so production changes require their own commit.

In a customer engagement, GitOps selects the approved application digest and runtime policy checks the trusted signature. A suitable VM container runtime can run that application digest. === Copy the verified image and its signatures

Tag the signed image into staging. The digest you print has to match the 5.1 digest, including the `sha256:` prefix. `oc tag` copies the image. `cosign copy` copies the signature tags from the build repository to the stage repository. `cosign sign --key` then signs that destination tag with the 5.3 key, which is what ImagePolicy will check. Each `cosign` command uses `/tmp/lab-home` for its registry configuration. The key path stays `/home/lab-user/lab-trust/cosign.key`.

.Tag, copy the signature, and sign the stage repository
[source,bash,role=execute]
----
BUILD_NS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_build_namespace}')"
PROMOTE_NS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_promote_namespace}')"
oc tag "${BUILD_NS}/spring-boot-lw-poc@${DIGEST}" "${PROMOTE_NS}/spring-boot-lw-poc:latest"
oc -n "${PROMOTE_NS}" get istag spring-boot-lw-poc:latest \
  -o jsonpath='{.image.metadata.name}{"\n"}'
TARGET_DIGEST="$(oc -n "${PROMOTE_NS}" get istag spring-boot-lw-poc:latest \
  -o jsonpath='{.image.metadata.name}')"
test "$TARGET_DIGEST" = "$DIGEST" || { echo "Copied digest differs from verified digest"; exit 1; }
SRC="image-registry.openshift-image-registry.svc:5000/${BUILD_NS}/spring-boot-lw-poc@${DIGEST}"
DST="image-registry.openshift-image-registry.svc:5000/${PROMOTE_NS}/spring-boot-lw-poc@${DIGEST}"
# oc tag copies the image, not .sig tags. Copy, then sign the dest repo with the 5.3 key.
mkdir -p /tmp/lab-home
HOME=/tmp/lab-home cosign login -u unused -p "$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" \
  image-registry.openshift-image-registry.svc:5000
HOME=/tmp/lab-home cosign copy --allow-http-registry --allow-insecure-registry "${SRC}" "${DST}"
HOME=/tmp/lab-home COSIGN_PASSWORD="" cosign sign --key /home/lab-user/lab-trust/cosign.key \
  --tlog-upload=false --allow-http-registry --allow-insecure-registry \
  "${DST}"
HOME=/tmp/lab-home cosign verify --key /tmp/track6-admission.pub \
  --insecure-ignore-tlog --allow-http-registry --allow-insecure-registry \
  "${DST}" > /tmp/track6-stage-verification.json
VERIFY_STATUS=$?
cat /tmp/track6-stage-verification.json
test "$VERIFY_STATUS" -eq 0 || { echo "Destination signature verification failed"; exit 1; }
----

=== Wait for node enforcement before starting stage

An `ImagePolicy` should appear in both namespaces. The object name comes from ConfigMap `lab-admission` key `policy_name`. The CronJob interval is about two minutes.

ImagePolicy reaches the node as a CRI-O policy file, written by the Machine Config Operator. `oc get imagepolicy` can succeed while the pools are still updating. Wait until both pools list the same updated count as the machine count, and `UPDATING` is `False`. Then set `replicas: 1`, push, and hard-refresh. That first pull is the one the node checks. A later restart of that same pod finds the image already on the machine and starts the container. In the Review, compare the Ready pod’s creation time with the ImagePolicy timestamp and confirm that the pools have finished updating.

.Start stage after the nodes are enforcing ImagePolicy
[source,bash,role=execute]
----
PROMOTE_NS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_promote_namespace}')"
PROD_NS="$(oc -n tssc-admission get configmap lab-admission -o jsonpath='{.data.prod_namespace}')"
POLICY="$(oc -n tssc-admission get configmap lab-admission -o jsonpath='{.data.policy_name}')"
ARGO="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_argocd_app}')"
oc -n "${PROMOTE_NS}" get imagepolicy "${POLICY}"
oc -n "${PROD_NS}" get imagepolicy "${POLICY}"
oc get mcp

=== Test an unsigned digest in the protected repository

== Key takeaways

* Admission is a namespaced `ImagePolicy` rendered from one TrustPolicy file.
* Start the stage Deployment after MachineConfigPools have applied that policy. A pull made before the node enforces it does not become Ready on a later restart.
* A service-account subject renders as `PublicKey` from the 5.3 ConfigMap `lab-cosign-pubkey`.
* `oc tag` needs a following `cosign copy`, and a `cosign sign --key` on the destination.
* Lightwell GAVs inside the image do not admit an unsigned tag.
* Production is a commit to a second remote, in the next module.
