= 6.1 Deploy the signed image with stage GitOps
:source-highlighter: rouge
:toc:
:toclevels: 2

In this module you prove that stage runs the signed digest, and that an unsigned tag on the same ImageStream fails at pull.

This is the first of the two modules in Track 6, which runs the signed Java application image as the production container and refuses an unsigned digest. You tag the signed image into `lw-poc-staging`, copy the signature onto that repository, commit the digest to the stage GitOps remote, and fill `admission/trust-policy.yaml`. A CronJob renders a namespaced `ImagePolicy` on `lw-poc-staging` and on `lw-poc-prod`. xref:module-16-prod-gitops.adoc[6.2 Promote to prod] is a second Gitea remote. Leave that remote for the next module. NetworkPolicy `app-operate` on staging stays open. That policy is not the xref:module-10-build-networkpolicy.adoc[4.3 Build NetworkPolicy] Check.

== Why this control exists

GitOps selects the exact digest to deploy. Runtime policy checks whether a pull from the protected repository carries a trusted signature. Unsigned deny is a pull failure, `ImagePullBackOff`, not an error from `oc apply`. The exact Lightwell versions inside the image do not admit an unsigned tag.

== Learning objectives

By the end of this module, you will be able to:

* Tag the signed image into `lw-poc-staging` and copy its signature onto that repository
* Commit the digest to the stage GitOps remote and leave `replicas` at 0 until the nodes are enforcing ImagePolicy
* Explain and configure the TrustPolicy fields that render a public-key ImagePolicy in stage and production
* Set `replicas: 1` only after both MachineConfigPools have finished applying that policy
* Distinguish a signature-related unsigned rejection from other pull errors while the signed stage pod remains Ready

== How GitOps and runtime policy work together

The admission file you edit on the stage remote is `admission/trust-policy.yaml`, `kind: TrustPolicy`. You set `enforce: true`, the live digest, and the pipeline service-account subject from 5.1. CronJob `trust-policy-apply` in namespace `tssc-admission` polls about every two minutes and renders `ImagePolicy` into both stage and prod. A `ClusterImagePolicy` does not satisfy this workshop’s required ImagePolicy evidence. Red Hat Advanced Cluster Security trusted image signers are a different gate.

Native `ImagePolicy` `signedEmail` has to be an email. The 5.1 identity is a Kubernetes service-account URI, so the CronJob renders `policyType: PublicKey` from ConfigMap `lab-cosign-pubkey`, the `cosign.pub` you published on 5.3. The TrustPolicy file still records the 5.1 service-account URI. That remains the Fulcio identity. `oc tag` copies the image and leaves the `.sig` tags behind. You `cosign copy` those tags, then `cosign sign --key` the destination repository, after the tag.

Lightwell Network and Lightwell Clearinghouse Premier are already inside the image as GAVs. Admission does not inspect Maven. A Premier member version does not skip unsigned deny.

image::track6-promotion-remotes.svg[Separate stage and production GitOps repositories carry the same verified digest to their own Argo CD Applications,width=700,link=self,window=blank]

As the figure shows, in this module you work the stage remote: `lw-student/gitops-spring-boot-lw-poc`, Application `lw-poc-staging`, namespace `lw-poc-staging`. Module 6.2 works the prod remote. Retargeting Application `lw-poc-prod` at the stage remote fails that later Check.

In a customer engagement you promote a signed digest with GitOps and admit only that identity. You commit to Gitea and fill TrustPolicy. The cluster renders `ImagePolicy`. A production virtual machine is the same digest on a different runtime, such as bootc or Satellite. This cluster has no virtual machine.

== The two remotes

ConfigMap `lab-gitea` in namespace `gitea` holds the URLs. `student_gitops_repo_url` is stage. `student_prod_gitops_repo_url` is prod. `student_promote_namespace` is `lw-poc-staging`. `student_build_namespace` is where the signed image lives. `student_argocd_app` is the stage Application. The password is the value of key `student_password`. Leave that value out of Git and out of screenshots.

ConfigMap `lab-admission` in namespace `tssc-admission` names the scored kind and the live kind. Success is the stage and prod URLs, the two namespaces, the Argo CD application name, and `scored=TrustPolicy` with `live=ImagePolicy`.

.Read the GitOps and admission coordinates
[source,bash,role=execute]
----
oc -n gitea get configmap lab-gitea \
  -o jsonpath='stage={.data.student_gitops_repo_url}{"\n"}prod={.data.student_prod_gitops_repo_url}{"\n"}promote_ns={.data.student_promote_namespace}{"\n"}build_ns={.data.student_build_namespace}{"\n"}argo={.data.student_argocd_app}{"\n"}'
oc -n tssc-admission get configmap lab-admission \
  -o jsonpath='scored={.data.scored_kind}{"\n"}live={.data.live_kind}{"\n"}hint={.data.unsigned_deny_hint}{"\n"}'
----

The seeded `admission/trust-policy.yaml` is deliberately incomplete. You will edit that file in your stage clone. The separate `admission-docs` example is reference material; it does not contain your repository scopes, verified digest, or signer identity.

== Exercise

=== Confirm the digest and admission key

Run these commands in the Showroom terminal. You need the final `image.txt` and verification outputs from Track 5, the existing private key, and the public key published in `tssc-admission/lab-cosign-pubkey`. Success means the saved digest still matches the build tag and the published public key matches your local key. If the tag moved, return to Track 5 and refresh the signing, policy, and SBOM evidence before continuing. Do not generate a replacement key here.

[source,bash,role=execute]
----
BUILD_NS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_build_namespace}')"
IMAGE="$(cat /home/lab-user/lightwell-signing-evidence/image.txt)"
CURRENT_IMAGE="$(oc -n "$BUILD_NS" get istag spring-boot-lw-poc:latest -o jsonpath='{.image.dockerImageReference}')"
[[ "$IMAGE" == *@sha256:* && "$IMAGE" == "$CURRENT_IMAGE" ]] || { echo "Return to Track 5: verified digest differs from build tag"; exit 1; }
DIGEST="${IMAGE##*@}"
test -f /home/lab-user/lab-trust/cosign.key || { echo "Recover your Track 5 signing key"; exit 1; }
oc -n tssc-admission get configmap lab-cosign-pubkey \
  -o jsonpath='{.data.cosign\.pub}' > /tmp/track6-admission.pub
cmp /home/lab-user/lab-trust/cosign.pub /tmp/track6-admission.pub \
  || { echo "Admission public key differs from your Track 5 key"; exit 1; }
printf 'Verified digest: %s\n' "$DIGEST"
----

=== Copy the verified image and its signatures

Tag the signed image into staging. The digest you print has to match the 5.1 digest, including the `sha256:` prefix. `oc tag` copies the image. `cosign copy` copies the signature tags from the build repository to the stage repository. `cosign sign --key` then signs that destination tag with the 5.3 key, which is what ImagePolicy will check. Each `cosign` command uses `/tmp/lab-home` for its registry configuration. The key path stays `/home/lab-user/lab-trust/cosign.key`.

.Tag, copy the signature, and sign the stage repository
[source,bash,role=execute]
----
BUILD_NS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_build_namespace}')"
PROMOTE_NS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_promote_namespace}')"
oc tag "${BUILD_NS}/spring-boot-lw-poc@${DIGEST}" "${PROMOTE_NS}/spring-boot-lw-poc:latest"
oc -n "${PROMOTE_NS}" get istag spring-boot-lw-poc:latest \
  -o jsonpath='{.image.metadata.name}{"\n"}'
TARGET_DIGEST="$(oc -n "${PROMOTE_NS}" get istag spring-boot-lw-poc:latest \
  -o jsonpath='{.image.metadata.name}')"
test "$TARGET_DIGEST" = "$DIGEST" || { echo "Copied digest differs from verified digest"; exit 1; }
SRC="image-registry.openshift-image-registry.svc:5000/${BUILD_NS}/spring-boot-lw-poc@${DIGEST}"
DST="image-registry.openshift-image-registry.svc:5000/${PROMOTE_NS}/spring-boot-lw-poc@${DIGEST}"
# oc tag copies the image, not .sig tags. Copy, then sign the dest repo with the 5.3 key.
mkdir -p /tmp/lab-home
HOME=/tmp/lab-home cosign login -u unused -p "$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" \
  image-registry.openshift-image-registry.svc:5000
HOME=/tmp/lab-home cosign copy --allow-http-registry --allow-insecure-registry "${SRC}" "${DST}"
HOME=/tmp/lab-home COSIGN_PASSWORD="" cosign sign --key /home/lab-user/lab-trust/cosign.key \
  --tlog-upload=false --allow-http-registry --allow-insecure-registry \
  "${DST}"
HOME=/tmp/lab-home cosign verify --key /tmp/track6-admission.pub \
  --insecure-ignore-tlog --allow-http-registry --allow-insecure-registry \
  "${DST}" > /tmp/track6-stage-verification.json
VERIFY_STATUS=$?
cat /tmp/track6-stage-verification.json
test "$VERIFY_STATUS" -eq 0 || { echo "Destination signature verification failed"; exit 1; }
----

=== Prepare the stage GitOps clone

Clone the stage GitOps remote, `student_gitops_repo_url`. A fresh clone does not inherit `git config` from the application repository. Set the author locally, the same identity as 3.2. The password is in the clone URL for this push. It does not belong in a committed file. Success is a clone at `/tmp/gitops-stage`.

.Clone the stage remote
[source,bash,role=execute]
----
STAGE_GITOPS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_gitops_repo_url}')"
: "${STUDENT_USER:=$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_username}')}"
: "${STUDENT_PASS:=$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_password}')}"
test ! -e /tmp/gitops-stage || { echo "Clone already exists: inspect and reuse it before continuing"; exit 1; }
hostpath="${STAGE_GITOPS#https://}"; hostpath="${hostpath#http://}"
git clone "https://${STUDENT_USER}:${STUDENT_PASS}@${hostpath}" /tmp/gitops-stage
cd /tmp/gitops-stage
git config user.name student
git config user.email student@workshop.local
----

=== Commit the stage digest with the application stopped

Open `/tmp/gitops-stage/values.yaml` in your editor. Set `image.digest` to the printed `$DIGEST`, including `sha256:`, and keep `replicas: 0`. Preserve the other chart settings. Review the diff before publishing: it should pin the image without starting a pod.

[source,bash,role=execute]
----
git diff --check
git diff -- values.yaml
git add values.yaml
git commit -m "Pin verified stage digest with replicas zero"
git push origin HEAD
----

Automated sync often stays on the previous commit, and `replicas: 0` can still look Healthy. After the push, hard-refresh the Application. Success of that refresh is sync status, health, and a Deployment whose `replicas` is `0`. Leave the pod stopped. A pull that happens before the node is enforcing ImagePolicy stores the image with no signature. After the policy is on that node, a restart reports `already present on machine` and `no signature exists`, and those retries do not start the container.

.Refresh the stage Application
[source,bash,role=execute]
----
ARGO="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_argocd_app}')"
PROMOTE_NS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_promote_namespace}')"
oc -n openshift-gitops annotate applications.argoproj.io "${ARGO}" \
  argocd.argoproj.io/refresh=hard --overwrite
oc -n openshift-gitops get applications.argoproj.io "${ARGO}" \
  -o jsonpath='sync={.status.sync.status} health={.status.health.status} rev={.status.sync.revision}{"\n"}'
oc -n "${PROMOTE_NS}" get deploy spring-boot-lw-poc \
  -o jsonpath='replicas={.spec.replicas} ready={.status.readyReplicas}{"\n"}'
----

image::track6-stage-readiness.svg[Commit the digest with zero replicas then render policy wait for node enforcement and start one signed replica,width=700,link=self,window=blank]

The sequence separates configuration from execution. A Synced, Healthy Application with zero replicas has no running application; you still need policy enforcement and a Ready pod.

=== Complete and publish the admission policy

Edit `/tmp/gitops-stage/admission/trust-policy.yaml` on the same stage remote. Leave `apiVersion` and `kind` as they are. Set `enforce: true`. Replace every `REPLACE_ME_*`. The issuer is `https://kubernetes.default.svc`, or the hint `oidc_issuer_hint` in ConfigMap `lab-admission`. The subject is the pipeline service-account URI from 5.1. The digest is the signed `sha256:…`. The scopes are the internal ImageStream repositories that staging and prod actually pull. Discover those names with `oc get is`. Confirm ConfigMap `tssc-admission/lab-cosign-pubkey` still holds the 5.3 PEM. The renderer obtains trust material from cluster configuration; keep PEM material out of the TrustPolicy file. The CronJob sets `signedIdentity.matchPolicy: ExactRepository` to the build ImageStream, so a pull in stage or prod accepts a signature whose identity is `lw-poc-build`.

image::track6-policy-flow.svg[The stage TrustPolicy and admission public key feed the CronJob which renders ImagePolicy for stage and production,width=700,link=self,window=blank]

As the figure shows, you edit the TrustPolicy file in Gitea. CronJob `trust-policy-apply` renders it. The live `ImagePolicy` then appears in `lw-poc-staging` and `lw-poc-prod`. `ClusterImagePolicy` and the Advanced Cluster Security signer list sit outside that gate.

Print the two repository scopes and the identity you verified in 5.1. Use these values to replace the seed fields; keep `metadata.name` and the existing `signedIdentity` block. Scopes are repository names without a tag or digest. The subject is the full service-account URI, not an email address.

[source,bash,role=execute]
----
PROD_NS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_prod_namespace}')"
printf 'stage scope: image-registry.openshift-image-registry.svc:5000/%s/spring-boot-lw-poc\n' "$PROMOTE_NS"
printf 'prod scope: image-registry.openshift-image-registry.svc:5000/%s/spring-boot-lw-poc\n' "$PROD_NS"
printf 'subject: https://kubernetes.io/namespaces/%s/serviceaccounts/pipeline\n' "$BUILD_NS"
printf 'issuer: https://kubernetes.default.svc\ndigest: %s\n' "$DIGEST"
grep -n 'REPLACE_ME' admission/trust-policy.yaml
----

After editing, `grep` should print nothing (exit status 1 means no matches). Inspect the file to confirm `enforce: true`, both scopes, and the exact digest and identity, then publish it. The CronJob reads the remote commit, so a local edit alone does not enable the gate.

[source,bash,role=execute]
----
git diff --check
git diff -- admission/trust-policy.yaml
git add admission/trust-policy.yaml
git commit -m "Enforce signed images in stage and production"
git push origin HEAD
----

=== Wait for node enforcement before starting stage

An `ImagePolicy` should appear in both namespaces. The object name comes from ConfigMap `lab-admission` key `policy_name`. The CronJob interval is about two minutes.

ImagePolicy reaches the node as a CRI-O policy file, written by the Machine Config Operator. `oc get imagepolicy` can succeed while the pools are still updating. Wait until both pools list the same updated count as the machine count, and `UPDATING` is `False`. Then set `replicas: 1`, push, and hard-refresh. That first pull is the one the node checks. A later restart of that same pod finds the image already on the machine and starts the container. The Check accepts the Ready pod created after ImagePolicy, once the pools are settled.

.Start stage after the nodes are enforcing ImagePolicy
[source,bash,role=execute]
----
PROMOTE_NS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_promote_namespace}')"
PROD_NS="$(oc -n tssc-admission get configmap lab-admission -o jsonpath='{.data.prod_namespace}')"
POLICY="$(oc -n tssc-admission get configmap lab-admission -o jsonpath='{.data.policy_name}')"
ARGO="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_argocd_app}')"
oc -n "${PROMOTE_NS}" get imagepolicy "${POLICY}"
oc -n "${PROD_NS}" get imagepolicy "${POLICY}"
oc get mcp
----

Do not continue until both pools show `UPDATED=True`, `UPDATING=False`, `DEGRADED=False`, and their updated and ready machine counts equal the machine count. Recheck `oc get mcp` while the change rolls out. Then edit only `replicas` to `1` in `/tmp/gitops-stage/values.yaml` and publish the change.

[source,bash,role=execute]
----
git diff --check
git diff -- values.yaml
git add values.yaml
git commit -m "Start stage after admission policy rollout"
git push origin HEAD
----

A hard refresh requests reconciliation; it does not prove that sync has finished. Repeat the Application inspection until its revision matches `git rev-parse HEAD` and it reports Synced and Healthy. The Deployment must have one Ready replica.

[source,bash,role=execute]
----
oc -n openshift-gitops annotate applications.argoproj.io "${ARGO}" \
  argocd.argoproj.io/refresh=hard --overwrite
oc -n "${PROMOTE_NS}" rollout status deploy/spring-boot-lw-poc --timeout=180s
oc -n "${PROMOTE_NS}" get pods -l app=spring-boot-lw-poc \
  -o 'custom-columns=NAME:.metadata.name,CREATED:.metadata.creationTimestamp,PHASE:.status.phase,READY:.status.containerStatuses[0].ready'
----

=== Test an unsigned digest in the protected repository

Native `ImagePolicy` is CRI-O `policy.json`. `oc apply` of an unsigned Deployment can succeed. The pod fails when the node pulls the image. If this cluster is using the Kyverno fallback, the deny happens at admission instead. Either way, read the pod and the events.

The gate covers `spec.scopes`. Tag an unsigned digest onto the same ImageStream and deploy that tag. Leave GitOps `image.digest` on the signed digest. Pointing GitOps at the unsigned tag would flap the Healthy check.

The throwaway pod should report `ImagePullBackOff` or a signature error. Confirm that the stage Application remains Healthy, the signed Deployment has `replicas=1`, and an `ImagePolicy` exists in both `lw-poc-staging` and `lw-poc-prod`. Both MachineConfigPools are done updating. The stage pod's creation time is later than that ImagePolicy. TrustPolicy has no `REPLACE_ME`, and `enforce` is `true`.

.Deny an unsigned tag, and confirm stage is still Healthy
[source,bash,role=execute]
----
BUILD_NS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_build_namespace}')"
PROMOTE_NS="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_promote_namespace}')"
ARGO="$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_argocd_app}')"
# Unsigned digest, in-scope name:
oc tag "${BUILD_NS}/openjdk-21-builder:latest" "${PROMOTE_NS}/spring-boot-lw-poc:unsigned"
oc -n "${PROMOTE_NS}" create deployment unsigned-deny-test \
  --image="image-registry.openshift-image-registry.svc:5000/${PROMOTE_NS}/spring-boot-lw-poc:unsigned"
oc -n "${PROMOTE_NS}" rollout status deploy/unsigned-deny-test --timeout=30s || true
oc -n "${PROMOTE_NS}" get pods -l app=unsigned-deny-test
oc -n "${PROMOTE_NS}" get events --field-selector reason=Failed --sort-by=.lastTimestamp \
  | tee /tmp/track6-unsigned-events.txt
----

Inspect `/tmp/track6-unsigned-events.txt` for the unsigned test pod's signature rejection. If only scheduling or pull progress appears, repeat the pod and event commands. Save the evidence, then remove the test and inspect the signed application.

[source,bash,role=execute]
----
cp /tmp/track6-unsigned-events.txt /home/lab-user/lightwell-signing-evidence/
oc -n "${PROMOTE_NS}" delete deployment unsigned-deny-test
oc -n openshift-gitops get applications.argoproj.io "${ARGO}" \
  -o custom-columns=NAME:.metadata.name,SYNC:.status.sync.status,HEALTH:.status.health.status
oc -n "${PROMOTE_NS}" get deploy spring-boot-lw-poc \
  -o jsonpath='replicas={.spec.replicas} ready={.status.readyReplicas}{"\n"}'
oc -n "${PROMOTE_NS}" get imagepolicy
oc -n lw-poc-prod get imagepolicy
POLICY="$(oc -n tssc-admission get configmap lab-admission -o jsonpath='{.data.policy_name}')"
echo -n "policy created "
oc -n "${PROMOTE_NS}" get imagepolicy "${POLICY}" -o jsonpath='{.metadata.creationTimestamp}{"\n"}'
oc -n "${PROMOTE_NS}" get pods -l app=spring-boot-lw-poc \
  -o 'custom-columns=NAME:.metadata.name,CREATED:.metadata.creationTimestamp,PHASE:.status.phase,READY:.status.containerStatuses[0].ready'
----

== Key takeaways

* Admission is a namespaced `ImagePolicy` rendered from one TrustPolicy file.
* Start the stage Deployment after MachineConfigPools have applied that policy. A pull made before the node enforces it does not become Ready on a later restart.
* A service-account subject renders as `PublicKey` from the 5.3 ConfigMap `lab-cosign-pubkey`.
* `oc tag` needs a following `cosign copy`, and a `cosign sign --key` on the destination.
* Lightwell GAVs inside the image do not admit an unsigned tag.
* Production is a commit to a second remote, in the next module.
