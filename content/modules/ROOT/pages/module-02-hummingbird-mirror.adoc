= 1.2 Mirror into the trust boundary
:source-highlighter: rouge
:toc:
:toclevels: 2

In this module you prove that the Hummingbird image you verified in the public catalog now sits on this cluster's registry, and that `cosign` still accepts its signature there.

This is the second module in Track 1, which defines the base image for the application you build on the Java runtime. xref:module-01-hummingbird-verify.adoc[1.1 Verify Hummingbird] checked the published pull spec. The Nexus Docker repository `hummingbird-mirror` starts empty. You finish the ImageSet, start Job `oc-mirror-student`, and verify the destination pull spec.

== Why this control exists

Later builds, GitOps, and admission pull the runtime base from inside the enterprise. The coordinate they use is this internal destination, and you can still verify it. You run the mirror so the signature arrives with the image.

In a customer engagement, a bastion host runs `oc-mirror` into the customer's registry. On this cluster the destination is in-cluster Nexus, hosted Docker repository `hummingbird-mirror`, exposed by Route `registry-lightwell-repo`. The Route host is specific to your cluster. You read it from ConfigMap `lab-lightwell-repo`. You still write the ImageSet, and you still start the run.

image::hummingbird-mirror-into-nexus.png["Published Hummingbird catalog already verified in 1.1, Job oc-mirror-student copying the image and signatures into the Nexus destination, and the Track 3 application that uses that destination pull spec",width=700,link=self,window=blank]

As the figure shows, module 1.1 already verified the published `hi/openjdk` pull spec, and the index digest stays the one you checked. In this module you start Job `oc-mirror-student`. `oc-mirror` copies the image, and `cosign copy` brings `.sig`, `.att`, and `.sbom` into the Nexus destination. You then run `cosign verify` on that destination. The repository name is `hummingbird-mirror`. The image path stays `hi/openjdk`. The host is the Route host you read from ConfigMap `lab-lightwell-repo`. The evaluation Job grades the lab. In Track 3 the application Dockerfile `FROM` uses this destination pull spec as the runtime base.

Lightwell Network and Lightwell Clearinghouse Premier remediate application libraries. Those libraries arrive through the Maven proxy in Track 2, as a separate input from this ImageSet. A Premier library still runs on this Hummingbird image at the destination. Track 3 binds `FROM` to the destination pull spec you record here.

[NOTE]
====
We use the Java `hi/openjdk` destination pull spec. A Hummingbird Python runtime follows the same pull spec and the same mirror. We call out Python.
====

[NOTE]
====
We use the in-cluster Nexus destination. A customer destination is often an Artifactory Docker remote or a local cache. The work is the same: an ImageSet, `oc-mirror` into that destination, then `cosign verify` on the internal pull spec. Artifactory is not installed here.
====

== Run oc-mirror

`oc-mirror` is already on the Showroom `PATH`. The mirror run is Job `oc-mirror-student` in namespace `lightwell-repo`. The Job manifest is key `job.yaml` on ConfigMap `oc-mirror-tooling`. That manifest already mounts the destination credentials and the workspace volume. You create the Job from that key. The Job does not exist until you create it.

The Job has two containers. The init container `oc-mirror` copies the image onto the destination. The stored command mirrors that image and leaves `--remove-signatures` out of the arguments. The signature tags are the next container: `copy-signatures` runs `cosign copy` from the published pull spec to the destination pull spec and writes `.sig`, `.att`, and `.sbom` tags beside the image. Nexus stores those objects as tags.

If a previous attempt still owns the name, delete it first. Success is `job.batch/oc-mirror-student created`.

.Create the student Job
[source,bash,role=execute]
----
oc -n lightwell-repo delete job oc-mirror-student --ignore-not-found
oc -n lightwell-repo get configmap oc-mirror-tooling \
  -o jsonpath='{.data.job\.yaml}' | oc create -f -
----

The mirror and the signature copy can take several minutes. Success is `condition met` for `complete`. The wait allows 20 minutes.

.Wait for the Job
[source,bash,role=execute]
----
oc -n lightwell-repo wait --for=condition=complete job/oc-mirror-student --timeout=20m
----

Read both containers. The init container `oc-mirror` is the image copy. The container `copy-signatures` is the tag copy.

The `oc-mirror` log prints two lines that are expected for this ImageSet. The `name` you set is one pull spec: the tag `21-runtime` and the index digest from 1.1. The warning includes `has both tag and digest : using digest to pull, but tag only for mirroring`. The next line says `No images by digests were mirrored. Skipping IDMS generation.` IDMS is an ImageDigestMirrorSet, the object that would redirect a later digest pull to a mirror. This ImageSet is mirrored under the tag, so `oc-mirror` skips that object. The copy still used the index digest from 1.1.

In the `copy-signatures` log, success is a line that starts with `DEST_PULLSPEC=`. The value is the destination host, the path `hi/openjdk`, the tag, and the same index digest as the published pull spec. Copy that whole line. The repository name `hummingbird-mirror` does not appear in it. In the **Check** section you run `cosign verify` on that destination pull spec. The evaluation Job looks for the pull spec in the ImageSet, a completed Job `oc-mirror-student`, and `.sig` tags on the destination.

.Read the Job logs
[source,bash,role=execute]
----
oc -n lightwell-repo logs job/oc-mirror-student -c oc-mirror
oc -n lightwell-repo logs job/oc-mirror-student -c copy-signatures

== Conclusion

Application images are built `FROM` a base. If that base is whatever `latest` pointed at on the public internet last Tuesday, every later signature, bill of materials, and admission decision is checking a name you no longer control. The control is to freeze one exact image name, digest included, prove Red Hat signed it, and copy that same digest into a registry you operate.

The digest is the point. A tag with no digest can be moved to different bytes after you looked at it. A name that includes `@sha256:` stays on the index you already checked.

=== Why the pipeline is verify, copy, verify

image::hummingbird-mirror-bases-pipeline.png["Mirror-bases pipeline: verify the published pull spec, copy the image and signature into the customer registry, verify the internal pull spec, and stop when verify fails",width=700,link=self,window=blank]

As the figure shows, the pipeline starts with `cosign verify` on the published pull spec. You already ran that check in module 1.1. A failed verify stops the mirror. In this module, `oc-mirror` copies the image and `cosign copy` brings `.sig`, `.att`, and `.sbom`. A failed copy stops the pipeline. You then run a second `cosign verify` on the internal pull spec. A failed verify there keeps builds off that destination. Job `oc-mirror-student` is how this lab runs the copy. The evaluation Job grades the lab.

You verify first, against the public catalog, with Red Hat's public key. If that check fails, you do not copy. Unsigned bytes, or bytes signed by some other key, stay out of your registry.

You then copy the image, and you copy the proof with it: the signature, the attestation, and the software bill of materials. Copying the image alone is a failed mirror. The second check will reject a registry that has the bytes and lost the signature.

You verify again, with the same public key, against the name inside your registry. If that check fails, builds do not use that destination. The usual causes are a copy that dropped the signature, a blob replaced after the copy, or a tag that was moved. The second check is what tells you the internal copy is still the image Red Hat signed.

Both checks name Red Hat's published public key, `https://security.access.redhat.com/data/63405576.txt`. `cosign verify` trusts the public key you give it. Red Hat signed `hi/openjdk` with the matching private key, so that signature validates against Red Hat's public key.

If you point the same command at a public key you generated, then the genuine image fails the check. The command succeeds again after the image is signed with your private key. The signed bytes can be the real base, a rebuild, or a substitute. The signature matches your key, so the check accepts them. The question the pipeline answers is then whether a holder of your key signed these bytes. For this base, the question you want answered is whether Red Hat signed this image.

This module rejects the wrong key when the snippet still points at `example.invalid`.

=== Why the lab made you do each step

xref:module-01-hummingbird-verify.adoc[1.1 Verify Hummingbird] is the check before the copy.

The cluster had already stored two different digests for this runtime. You printed both so you could see they are not interchangeable. One is the catalog name, the image index: the line you verify and later copy. The other is the amd64 platform image inside that index, which is what this cluster would run. An arm64 entry can sit in the same index. This lab never verifies that architecture. It only shows that one catalog name can list more than one. The check uses the catalog name.

You wrote that catalog name and Red Hat's public key into a small script, then ran `cosign verify`. You did that so you could see the signature yourself: the claims validate, and the signature matches that public key. The lab skips the public transparency log and warns about it. A customer command does not skip that log. The exercise rejects a leftover example image, `ubi-minimal`, and a leftover example key, because either one would make the check pass against the wrong thing.

You printed the internal registry coordinates first, including a flag that the scored image was not already there. You need the host for this cluster from the cluster, because that hostname is different on every environment. You also saw that the Nexus repository name, `hummingbird-mirror`, is the place the registry stores the image. It is not part of the image path developers will write. The path stays `hi/openjdk`. The host changes to yours. The digest stays the one you verified.

You put that same catalog name into an `ImageSetConfiguration`. That file is the list `oc-mirror` is allowed to copy. The lab left a placeholder, and it left a worked example that names a generic Universal Base Image. You replaced the placeholder with the signed runtime. Pasting the example would copy the wrong image and still look like a successful mirror.

You started Job `oc-mirror-student`. That job is this cluster's stand-in for the bastion. It has two steps on purpose. The first copies the image and is told not to strip signatures. The second runs `cosign copy` and writes the signature, attestation, and bill of materials beside the image. This registry stores those objects as tags. You waited until the job completed, then read `DEST_PULLSPEC`. That line is the internal name: your registry host, `hi/openjdk`, and the same digest. You verify that line. Verifying `registry.access.redhat.com` again is the first module.

You ran `cosign verify` on it with the same Red Hat public key. The registry in the lab uses a local certificate, so the command allows that. Success is the same two results as the first module, now printed for your host. That is the evidence the bytes inside your registry are still the signed image.

The graded jobs at the end of each module are workshop scoring. They read what you wrote down: the verify script, the image list, a finished copy job, the signature tags, and a short report token. They do not run `cosign`. You ran `cosign` because that is the control. Leave those grader jobs out of a customer cluster.

=== How you run this on your estate

Red Hat's mirror procedure is something you repeat when the catalog changes. The host that reads the public catalog needs a path to it. If that host can also reach your registry, `oc-mirror` copies straight across, which is what this lab did. If the registry is fully disconnected, the connected host writes a disk archive, the archive crosses the boundary, and a host next to the registry loads it.

A bastion runs that procedure. Start it with cron or a systemd timer. Ansible Automation Platform can wrap the same commands in a job template and schedule that template against the bastion. Jenkins, GitLab CI, or OpenShift Pipelines can run it as a pipeline whose only work is this mirror. The part that downloads from Red Hat still needs a path to the public catalog. On a fully disconnected cluster, that pipeline loads the disk archive a connected host already wrote.

Keep this pipeline on the platform side. Application pipelines sign the application image, apply policy, and refuse an unsigned digest at deploy. Those are later controls. They assume this base is already inside your registry and still verifies.
