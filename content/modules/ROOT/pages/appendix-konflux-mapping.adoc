= Appendix: Konflux terminology and workshop equivalents
:toc:
:toclevels: 2

Use this table when a delivery discussion uses Konflux terminology. The workshop implements related controls with OpenShift Pipelines and other installed services. These are functional comparisons, not claims that the products are interchangeable or that Konflux is installed.

== Compare responsibilities

[cols="2,3,2",options="header"]
|===
|Term in a delivery discussion |What the workshop uses |Where to inspect it
|Konflux build pipeline
|OpenShift Pipelines orchestrates Tasks; an OpenShift BuildConfig builds the application image.
|xref:module-11-build-sbom.adoc[4.4 Build and SBOM]
|Hermeto dependency prefetch
|Task `prefetch-dependencies` in `lightwell-tasks` prepares the Maven cache from Nexus. The build consumes it with offline Maven.
|xref:module-09-prefetch.adoc[4.2 Prefetch]
|Buildah image build
|The pipeline starts a binary BuildConfig with `oc start-build --from-dir`. There is no separate Buildah Task in this path.
|xref:module-11-build-sbom.adoc[4.4]
|MintMaker dependency updates
|An in-cluster Renovate bot opens a Gitea PR for the learner to review and merge.
|xref:module-07-live-renovate.adoc[3.3 Live Renovate]
|Tekton Chains and provenance
|Task `cosign-sign-keyless` signs the application through RHTAS. This is image signing; the workshop does not generate a Chains provenance attestation.
|xref:module-12-sign-keyless.adoc[5.1 Keyless signature]
|Conforma policy
|Task `conforma-policy` evaluates the learner's policy copy. The exercise compares signature results for an unsigned builder and the signed application.
|xref:module-13-attest-conforma.adoc[5.2 Signature policy]
|Release Service
|A separate production GitOps commit selects the verified digest, and Argo CD reconciles the deployment.
|xref:module-16-prod-gitops.adoc[6.2 Production promotion]
|Image vulnerability and policy assessment
|Task `acs-image-check` calls ACS. Module 7.2 inspects a direct TaskRun against the promoted image and configures future pipeline checks to fail on a skip.
|xref:module-18-vex-acs.adoc[7.2 ACS evidence]
|===

== Keep policy and provenance distinct

Module 5.2 retains an expected attestation-signature exception because this lab does not produce the corresponding provenance attestation. Read the policy reports as image-signature evidence. Neither keyless signing nor a successful image-signature check establishes a SLSA level.

Track 6 uses TrustPolicy and ImagePolicy to enforce image signatures during runtime image pulls. ACS performs a separate image policy assessment. When explaining an outcome, name the control that produced it and show its result.

== Apply the comparison

Use the installed Task and resource names when inspecting the cluster or editing the application pipeline. For a customer using Konflux, map the required inputs, outputs, identities, and acceptance policies to that platform, then validate the actual implementation.

See xref:appendix-consultant-delivery.adoc[Consultant delivery map] for the broader activities and xref:appendix-enablement-checklist.adoc[Delivery readiness review] for evidence to discuss after the workshop.
