:source-highlighter: rouge

:toclevels: 2

Tracks 1 and 2 produced a verified Hummingbird destination and an exact Lightwell dependency version. In Track 3 you record those choices in application source that you own, then review an automated update. Work in the Showroom terminal and the in-cluster Gitea UI.

This first module creates your application and GitOps repositories. Module 3.2 commits the base image and dependency version; module 3.3 merges a Renovate pull request. Keep those steps in order so each module starts with the previous module's result.

== Why this control exists

Templating gives each application a consistent starting point: prepared source code, build files, and deployment configuration that your team can reuse instead of assembling them from scratch. This reduces setup mistakes and makes shared conventions easier to maintain. In this module, you use a seed script to copy the workshop templates from `workshop-templates` into your own `lw-student` repositories on Gitea. The lab deliberately leaves some inputs unfinished so you can apply and verify the controls yourself.

That starting point also needs maintenance as dependencies and base images change. Renovate is an automated tool that checks for available updates and proposes them through pull requests. It helps you notice version changes without checking every dependency manually, while keeping the decision to accept an update with you. The pull request gives you a diff to review and a Git history of the proposed and accepted changes; an available update alone does not prove that it is safe for your application.

You use both controls across Track 3. After seeding your repositories here, you commit the verified Hummingbird runtime and exact Lightwell dependency version in xref:module-06-bind-base-deps.adoc[module 3.2]. In xref:module-07-live-renovate.adoc[module 3.3], the in-cluster `renovate-bot` proposes updates to the dependency version and image digest recorded in `lightwell-pins.properties`. You compare both values with your earlier evidence, then merge the pull request in Gitea. That properties-file update does not rewrite the Dockerfile or Maven POM. Committing and pushing your edits, or merging the reviewed pull request, records your choices in the shared repository that later builds and validation Jobs read.

image::gitea-templates-vs-learner-org.png[Workshop templates copied into student-owned lw-student remotes,width=700,link=self,window=blank]

The application repository holds the Java code and build files. The two GitOps repositories hold deployment configuration for stage and production in Track 6. You create all three here so the rest of the workshop has a consistent source location.

== Learning objectives

By the end of this module, you will be able to:

* Identify the template and student application URLs in cluster configuration.
* Create the student organization and three empty repositories on Gitea.
* Seed the repositories and confirm that the application contains the expected starting files.
* Explain why later builds must read your student remote instead of the template.

== The Gitea coordinates

ConfigMap `lab-gitea` in namespace `gitea` holds the URLs. `gitea_url` is the console. `student_username` is `student`. `student_gitea_org` is `lw-student`. `student_repo_url` is the scored application remote. `template_app_repo_url` is the operator tree you copy from. The password is the value of key `student_password`. Leave that value out of Git and out of screenshots.

Check that each URL has a value, the user is `student`, and the organization is `lw-student`. The command displays repository coordinates without printing the password.

[source,bash,role=execute]
----
oc -n gitea get configmap lab-gitea \
  -o jsonpath='gitea_url={.data.gitea_url}{"\n"}user={.data.student_username}{"\n"}org={.data.student_gitea_org}{"\n"}app={.data.student_repo_url}{"\n"}templates={.data.template_app_repo_url}{"\n"}'
----

The seed Job may already have created the `student` account. The ensure script is a no-op when the account exists. Success is a script that exits 0.

.Ensure the Gitea user can sign in
[source,bash,role=execute]
----
export STUDENT_USER=student
: "${STUDENT_PASS:=$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_password}')}"
: "${GITEA_URL:=$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.gitea_url}')}"

oc -n gitea get configmap gitea-student-repo-seed \
  -o jsonpath='{.data.student-ensure-gitea-user\.sh}' > /tmp/student-ensure-gitea-user.sh
chmod +x /tmp/student-ensure-gitea-user.sh
/tmp/student-ensure-gitea-user.sh
----

Open `gitea_url` and sign in as `student` using your lab Gitea password.

=== Seed the prepared source

The seed script copies the template tree and adds `renovate-bot` as a write collaborator on the application repository. Success is a script that exits 0.

.Seed from the templates
[source,bash,role=execute]
----
export STUDENT_USER=student
: "${STUDENT_PASS:=$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_password}')}"
: "${GITEA_URL:=$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.gitea_url}')}"

oc -n gitea get configmap gitea-student-repo-seed \
  -o jsonpath='{.data.student-seed-from-templates\.sh}' > /tmp/student-seed.sh
chmod +x /tmp/student-seed.sh
/tmp/student-seed.sh
----

== Review

Compare the student URL with the template URL. They should use the same in-cluster Gitea host and different organizations: `lw-student` and `workshop-templates`. The HTTP request should return `200`. This confirms that the repository page is reachable; inspect its files next.

[source,bash,role=execute]
----
oc -n gitea get configmap lab-gitea \
  -o jsonpath='{.data.student_repo_url}{"\n"}{.data.template_app_repo_url}{"\n"}'
curl -sk -o /dev/null -w "%{http_code}\n" \
  "$(oc -n gitea get configmap lab-gitea -o jsonpath='{.data.student_repo_url}')"
----

== Applying this pattern elsewhere

A Red Hat Developer Hub software template can publish prepared source into a team's Git organization. This lab uses a seed script for that step. Lightwell supplies dependencies; Gitea owns the application history that records their versions.
