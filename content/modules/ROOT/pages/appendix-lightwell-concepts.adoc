= Appendix: Lightwell concepts (FAQ distill)
:toc:
:toclevels: 2

Optional reference for instructors and students. Distills technical concepts that appear in field Lightwell enablement into workshop language. It does *not* replace the seven gated tracks, and it omits commercial SKUs, pricing, competitor comparisons, and associate-only sales guidance.

Hands-on work stays in the core modules. Use this module when a student asks “what does Validated mean?” or “does Lightwell go through Satellite?”

== Product definition

[cols="1,2",options="header"]
|===
|Question |Workshop answer

|What problem does Lightwell solve?
|Scanners/SBOMs find vulns; teams often cannot upgrade. Lightwell supplies surgical security backports on exact versions recorded in source.

|What is Lightwell Network vs Lightwell Clearinghouse Premier?
|*Network* (available) is catalog remediations: Validated and Remediated repos consumed through existing build and artifact-manager workflows. *Clearinghouse Premier* (limited availability) includes all Network benefits plus member-specific package versions, novel vulnerability verification and disclosure handling (secured patch embargoes), anonymized member requests, and TAM services. This lab scores the Network path. Premier remediations would use the same proxy, exact version, hermetic build, and TPA ingest (xref:index.adoc[workshop home]). Product page: link:{lightwell-product-url}[Lightwell^].

|What is an embargo?
|An *embargo* is a coordinated-disclosure window. The vulnerability and its patch stay inside a closed member set until a public date. Clearinghouse Premier can deliver that member version during the window, as an exact `.rhlw-*` or `+rhlw.*` version. Lightwell Network's documented lifecycle ends at public *Disclosure*, when VEX and OSV go to the broader ecosystem (link:{docs-lwn-lifecycle-url}[Patch delivery lifecycle^]). This workshop scores the post-disclosure Network path. The controls are the same. What changes is when the public advisory exists. This cluster has no embargo exercise. Legal embargo-contract enforcement stays off the cluster.

|What is in scope?
|Signed remediations and supply-chain artifacts for eligible third-party *application* dependencies (libraries, frameworks, build tools, transitive deps), CVE triage metadata, SBOM/VEX, and related attestations.

|What is out of scope for this lab path?
|Proprietary code scanning, penetration testing, feature bug fixes, Satellite content views, inventing alternate channel names, a live Premier membership or member-specific GAV on this cluster.

|Which ecosystems?
|The lab application is a Java greeting service built with Maven. A request to `/api/greeting` returns a hello message. Python (PyPI) uses the same Validated / Remediated idea. Do not promise unannounced ecosystems.
|===

== Repositories and versioning

[cols="1,2",options="header"]
|===
|Question |Workshop answer

|What is the Lightwell *Validated* repository?
|Community source code, built by Red Hat. Guaranteed, signed provenance -- no "mystery blobs" from the Internet. Does not contain backported patches, but lets you be confident that the code you see is the code you're running.

|What is the Lightwell *Remediated* repository?
|Older community libraries kept at an exact version, with backported security-only patches. Allows you to stay on your version of an open-source library, while still receiving security updates. Java uses `.rhlw-#####` (labs use `.rhlw-0000X`); Python / pip uses PEP 440 local `+rhlw.#####` (workshop seeded marker `1.0.0+rhlw.00001`).

|What is the Lightwell *Predisclosure* repository?
|Similar to Lightwell Remediated, but also includes patches for embargoed, not-yet-public vulnerabilities. Used for maintaining live production applications with robust CI/CD support, ensuring that patches are already in place when a vulnerability goes public.

|When do packages get promoted between Predisclosure, Remediated, and Validated?
|*Predisclosure*, *Remediated*, and *Validated* repositories are independently-maintained branches. Compiled binaries are not "promoted" from one repository to another. Instead, a code change that fixes a vulnerability in Predisclosure will be reimplemented and rebuilt in Remediated once the vulnerability goes public. Since Validated is guaranteed to exactly match the open-source community, a fix will only appear in Validated when (or if) the community implements the fix.

|How do I find status?
|Console for Validated browse ({lightwell-console-url}). OSV metadata for Remediated CVE ↔ `.rhlw-*` mapping (xref:module-04-remediated-pin.adoc[2.2]).

|Are sources available?
|Yes—source archives ship beside binaries in the same repos (xref:module-04-remediated-pin.adoc[2.2] source diff).

|How are new packages noticed?
|Poll the OSV feed (optional xref:appendix-osv-manifest-polling.adoc[PULP_MANIFEST] automation).
|===

== Integration

[cols="1,2",options="header"]
|===
|Question |Workshop answer

|How do build tools integrate?
|We use Maven against Nexus, and an artifact manager such as Artifactory. On this cluster the artifact manager is Nexus. We call out `pip`. Artifactory map: remote to Lightwell URL, virtual for developers, include/exclude so Lightwell GAVs do not fall through to Central. xref:module-03-enterprise-proxy.adoc[2.1].

|Air-gapped?
|Same mirror/proxy patterns used for other Red Hat content—not a unique LWN-only protocol.

|Via Satellite?
|No. Consume via artifact repository infrastructure (`packages.redhat.com` / enterprise manager).

|Non-RHEL runtimes?
|Yes—application-layer libraries can run on non–Red Hat OS/stacks.

|Customer testing?
|Red Hat runs upstream/regression checks before publish; application-context testing remains the consumer’s responsibility.
|===

== OSV, SBOM, and pipelines

Acronym expansions: xref:appendix-acronyms.adoc[Acronym glossary]. First teaching definitions also appear in the workshop xref:index.adoc[home module].

[cols="1,2",options="header"]
|===
|Question |Workshop answer

|OSV id shape?
|Production: `RHLW-YYYY-NNNN`. Workshop sample: `LW-DEMO-0001`. `fixed` events point at `.rhlw-*`.

|Are AI models named in OSV?
|No—discovery source stays anonymous; credits identify Red Hat Lightwell as remediation developer.

|Compliance artifacts?
|SLSA L3, cryptographic signing (RHTAS-class), CycloneDX + VEX for Maven, SPDX for Python wheels.

|CI scanners (Snyk-class tools)?
|Consume OSV/VEX so Lightwell-patched CVEs are recognized as remediated (xref:module-18-vex-acs.adoc[7.2]).

|Proprietary source to Red Hat?
|No—manifests and SBOMs, not application source trees.
|===

== Coexistence

[cols="1,2",options="header"]
|===
|Question |Workshop answer

|vs RHEL / OpenShift / ACS?
|Complementary. Platform products cover OS/platform; Lightwell covers third-party app deps. xref:module-18-vex-acs.adoc[7.2] scores ACS with the remediated version.

|vs Hardened Images?
|Hardened Images address container *foundations*; Validated/Remediated address *application* dependencies.

|vs TSSC (RHTAS, RHTPA, GitOps, Pipelines)?
|TSSC is the *controls* around the image (sign, SoR, admit, hermetic build). Lightwell Network (and Premier) is a *trusted input* those controls consume. Neither replaces the other. See xref:index.adoc[workshop home].

|vs IBM LSOS?
|LSOS extends selected EOL Java frameworks; Lightwell backports across a broad catalog with registry/signing/SBOM story. Not exercised in this workshop.
|===

* Competitor positioning
* International sales / export / federated clearinghouse policy

* Live air-gap sync Job beyond the seeded/proxy modes already in xref:module-03-enterprise-proxy.adoc[2.1]
* Embargo *contract* enforcement (legal / disclosure frameworks). The concept is the answer to “What is an embargo?” above, and xref:module-04-remediated-pin.adoc[2.2] shows where the exact version is recorded.
