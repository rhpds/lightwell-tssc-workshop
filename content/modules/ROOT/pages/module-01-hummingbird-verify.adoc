= 1.1 Verify Hummingbird
:source-highlighter: rouge
:toc:
:toclevels: 2

In this module you prove that the Java runtime base is a published Hummingbird image, and that its signature matches Red Hat's key, while that image still lives in the public catalog.

This is the first of the two modules in Track 1, which defines the base image for the application you build on the Java runtime. You read the pull spec from ConfigMap `lab-lightwell-repo` and run `cosign verify` against that published digest. xref:module-02-hummingbird-mirror.adoc[1.2 Mirror into the trust boundary] copies that same pull spec into the cluster.

The image is a Project Hummingbird runtime in link:{docs-hardened-images-url}[Red Hat Hardened Images^]. The scored image is `hi/openjdk`. Red Hat signs the catalog image. This cluster consumes that signature.

== Why this control exists

A trusted software supply chain starts with a trusted runtime input. That input is a specific name your organization already uses: the published pull spec, digest included. Later signatures, SBOMs, and admission decisions refer back to that name. You check it here, in the catalog Red Hat published.

Red Hat Hardened Images is that runtime: a minimal signed image under `registry.access.redhat.com/hi/…`, with no package manager in the image. A Universal Base Image is a general-purpose base. This module uses the Hardened Images pull spec the cluster stores in ConfigMap `lab-lightwell-repo`.

image::hummingbird-catalog-nexus-app.png["Published Hummingbird catalog, then the Nexus destination, then the application image that uses that base",width=700,link=self,window=blank]

As the figure shows, in this module you work the box on the left: `cosign verify` on the published catalog. In the next module you fill the internal destination in Nexus. In Track 3 you set the application image that uses that base.

Lightwell Network and Lightwell Clearinghouse Premier remediate application libraries. Those libraries run on this base. A Premier member package still needs this verified Hummingbird pull spec underneath it.

[NOTE]
====
A Hummingbird Python runtime (`hi/python`, or the name your catalog uses) follows the same verify. This Check scores the Java `hi/openjdk` pull spec from ConfigMap `lab-lightwell-repo`.
====

In a customer engagement, the customer subscribes to Hardened Images and records the digest in their catalog. Red Hat runs the factory and holds the signing key. Here you do the consumer half: read the pull spec, verify it, and carry that same pull spec into the mirror.

== Learning objectives

By the end of this module, you will be able to:

* Verify a published Hardened Images digest with `cosign` and Red Hat's key
* Read the pull spec from ConfigMap `lab-lightwell-repo` and pass that string to `cosign verify`
* Explain the image index and the amd64 manifest inside it, and recognize an arm64 entry as an example of a second architecture the labs do not use

[#published-pull-spec]
== The published pull spec

The cluster has been prepared with two digests for the published Hummingbird runtime `hi/openjdk`. Verify the digests by running the following commands.

.Read the pull spec
[source,bash,role=execute]
----
oc -n lightwell-repo get configmap lab-lightwell-repo \
  -o jsonpath='{.data.hummingbird_source_pullspec}{"\n"}'
----

.Read the amd64 manifest
[source,bash,role=execute]
----
oc -n showroom get configmap lab-showroom \
  -o jsonpath='{.data.hummingbird_amd64_manifest}{"\n"}{.data.hummingbird_source_registry}{"\n"}'
----

As you can see, the two digests describe the `hi/openjdk` image. The first command prints the pull spec: one line with `registry.access.redhat.com`, `hi/openjdk`, and `@sha256:`. The digest after `@` is the image index, one manifest that can list more than one architecture. ConfigMap `lab-lightwell-repo` in namespace `lightwell-repo` stores that line as `hummingbird_source_pullspec`. The second command prints a different `sha256:`, then `registry.access.redhat.com`. That sha256 is the amd64 manifest, the platform image this cluster runs. ConfigMap `lab-showroom` in namespace `showroom` stores it as `hummingbird_amd64_manifest`. The same index may also list arm64. That listing is an example, and the labs do not use it. It shows that one index can list more than one architecture. In the **Exercise** section you pass that pull spec to `cosign verify`.

Red Hat signs every Hardened Images catalog image at build time. This Showroom shell already has `cosign` on `PATH`. On a Red Hat Enterprise Linux host the same key is a file under `/etc/pki/sigstore`, and the product documentation mounts that directory into a `cosign` container. This terminal has no such directory, so the Exercise uses the URL below.

The key URL is `https://security.access.redhat.com/data/63405576.txt`. The Exercise command includes `--insecure-ignore-tlog`, which skips the transparency log and checks the signature against that key. This Showroom `cosign` warns that skipping the log is insecure. Success is the two checks under that warning: the cosign claims were validated, and the signatures were verified against the specified public key. See link:{docs-hardened-images-url}[Verify the integrity of Red Hat Hardened Images^].

Track 5 signs your application image with in-cluster Red Hat Trusted Artifact Signer. That signature uses a short-lived Fulcio certificate. This module uses Red Hat's published Hardened Images key. If the key URL fails to load on this cluster, stop and tell an instructor.

The block has the same flags you will use, and the wrong two arguments. `--key` points at `example.invalid`, which does not serve Red Hat's public key, so `cosign` cannot download it. The image is `ubi9/ubi-minimal:latest`, not the `hi/openjdk` pull spec you read above. Running the block fails on purpose. The Exercise runs `cosign verify` with that pull spec and `https://security.access.redhat.com/data/63405576.txt`.

[source,bash]
----
# Worked example ONLY — ubi-minimal, and a key outside Red Hat Hardened Images.
cosign verify \
  --key https://example.invalid/not-redhat-hardened-images.pub \
  --insecure-ignore-tlog \
  registry.access.redhat.com/ubi9/ubi-minimal:latest
----

== Exercise

`cosign` is already installed in the Showroom terminal. You use it here. You use `oc-mirror` in the next module.

Use the pull spec you read in <<published-pull-spec,The published pull spec>>. That line contains `registry.access.redhat.com`, `hi/openjdk`, and `@sha256:`. The amd64 sha256 from the second command is a different digest. Pass the pull spec to `cosign verify`, not the amd64 digest.

The command reads that pull spec again from ConfigMap `lab-lightwell-repo` and verifies it with Red Hat's key. Success is exit code 0, the tlog warning, and the two checks under the warning.

.Verify the published pull spec
[source,bash,role=execute]
----
PULLSPEC="$(oc -n lightwell-repo get configmap lab-lightwell-repo -o jsonpath='{.data.hummingbird_source_pullspec}')"
cosign verify \
  --key https://security.access.redhat.com/data/63405576.txt \
  --insecure-ignore-tlog \
  "$PULLSPEC"
----

== Review

The command succeeded when the output names the `hi/openjdk` pull spec and then prints these two checks:

[source,text]
----
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - The signatures were verified against the specified public key
----

A warning above those lines says tlog verification was skipped. That warning is expected with `--insecure-ignore-tlog`. The two checks are the proof that Red Hat signed this pull spec.

[#module-01-conclusion]
== Conclusion

Red Hat publishes Hardened Images, including the Hummingbird runtime `hi/openjdk`, for a customer to use as an application base. The customer subscribes and records one pull spec. Red Hat builds the image and holds the signing key. You keep the public key and use it to check the signature.

A bastion host, or a pipeline whose only job is to mirror bases, copies that image into the customer registry. `oc-mirror` copies the image and leaves the signatures in place. `cosign copy` then brings the signature, attestation, and SBOM to the same destination. Those two steps do not use a key the customer owns. `cosign verify` comes before the copy and again after it, both times with Red Hat's published public key, `https://security.access.redhat.com/data/63405576.txt`. The first check accepts the published pull spec. The second check accepts the internal pull spec. The command you ran adds `--insecure-ignore-tlog` because the Showroom skips the transparency log. The customer command below is the verify without that flag.

image::hummingbird-mirror-bases-pipeline.png["Mirror-bases pipeline: verify the published pull spec, copy the image and signature into the customer registry, verify the internal pull spec, and stop when verify fails",width=700,link=self,window=blank]

As the figure shows, the pipeline starts with `cosign verify` on the published pull spec. That is the check you run in this module. A failed verify stops the mirror. The next module copies the image with `oc-mirror` and brings `.sig`, `.att`, and `.sbom` with `cosign copy`. A failed copy stops the pipeline. A second `cosign verify` then accepts the internal pull spec. A failed verify there keeps builds off that destination.

The example uses names you replace with the customer's registry. It is not a command to run on this cluster. The next module is where you mirror.

[source,bash]
----
# Bastion or mirror pipeline. Not a command on this cluster.
PUBLISHED=registry.access.redhat.com/hi/openjdk:21-runtime@sha256:INDEX
DEST=registry.example.com/hi/openjdk:21-runtime@sha256:INDEX
KEY=https://security.access.redhat.com/data/63405576.txt

cosign verify --key "$KEY" "$PUBLISHED"
# oc-mirror that pull spec into the customer registry.
# cosign copy brings .sig, .att, and .sbom to $DEST.
cosign verify --key "$KEY" "$DEST"
----

A failed `cosign verify` stops that pipeline. The first verify fails when the published image has no signature, the signature does not match Red Hat's public key, or the pull spec is not the signed index. The bastion does not mirror. Those bytes stay out of the customer registry. The copy can still fail on its own: `oc-mirror` errors, or `cosign copy` never writes `.sig`, `.att`, and `.sbom` beside the image. The second verify then fails, and builds do not receive that destination pull spec.

The second verify also fails when the internal registry no longer holds the signed bytes. A tag with no digest can be moved to a different build after you verified an older one. A digest pull spec keeps the mirror on the index you already checked. Replacing the blob in the customer registry, or dropping the signature on the way in, leaves an image `cosign verify` rejects. The pipeline uses Red Hat's published key on both commands. A verify that uses some other key can accept a signature Red Hat did not create. The worked example fails for that reason: its key is not Red Hat's, and its image is not `hi/openjdk`.

That procedure wraps the mirror for each Hardened Images base the customer consumes. It stays on the platform side. Later tracks sign the application image, apply policy, and refuse an unsigned digest at deploy. Those controls belong on the application pipeline. This verify does not.
